## Parametri numerici respinti come stringhe

- `read_file` con `start_line`/`end_line` e `terminal` con `timeout_ms` possono fallire con `invalid type: string, expected u32/u64` anche con valori numerici → non insistere: per i range usare `sed -n '<A>,<B>p' <file>` via terminal; per `terminal` omettere `timeout_ms` (il default basta per comandi brevi).

## Batch `edit_file` non atomico

- Se un edit del batch non combacia, la chiamata si interrompe: gli edit **prima** sono applicati, quelli **dopo** no → dopo un failure, rileggere il file e riapplicare solo i mancanti con il testo esatto corrente.
- Un formatter/reflow tra un turno e l'altro può spezzare liste YAML/Markdown (es. `tests: [a, b]` su più righe) e far fallire `old_text` multiriga → preferire ancore a riga singola o rileggere sempre prima di un nuovo batch.
- File condivisi mutati da sessioni parallele tra lettura e scrittura invalidano le ancore come il reflow (es. `./ToDo.md` o questi reference, con delta/evidenze accodati da altre sessioni): rileggere prima di ogni batch. Non usare due edit a cascata con ancore sovrapposte nello stesso batch: se l'edit prima rimuove parte del testo che l'edit dopo usa come ancora, si tronca contenuto (stato intermedio applicato) → una inserzione = un edit.

## Writer canonico per handoff JSON

- `product/state/handoff-<kind>.json` si scrive con `bash agents/scripts/harness-prompt-builder.sh handoff-write <kind> --field summary='…' --field files=… --field next=…` (default `product/state/` **risolto dalla root dello script**, `ts`/`cmd`/`token_budget` auto-compilati), non con `write_file` a mano: la scrittura manuale rischia schema drift e campi stale; dove i comandi citano `scripts/harness-prompt-builder.sh`, dalla root HAL il path va risolto in `agents/scripts/`.

## Processi distaccati via tool MCP: timeout ≠ esito, mai fidarsi di pgrep
- Un tool-a-figli (es. `test_run`) che supera il timeout del context server risponde «Context server request timeout» ma il subprocess può essere sopravvissuto ORFANO (caso h2b laya 2026-11-05: job completato server-side mentre il secondo tentativo veniva fermato come zombie) OPPURE essere stato ucciso a metà (caso d9 laya 2026-11-09: `update-and-deploy.sh` morto durante il build torch, container già rimosso dal `compose down` → servizio giù ~25 min). Regola: dopo un timeout MCP NON assumere né successo né fallimento — misurare l'esito reale (tag/ID image, artefatti, `docker inspect` created, righe DB).
- Per operazioni lunghe distruttive-parziali (deploy che fa down→build→up) usare `setsid nohup <cmd> > /tmp/<log> 2>&1 &` e pollare il log, non il tool: la sequenza degradata corretta osservata in d9 = ripristino immediato sull'ultima image nota (`compose up -d` senza build) → rebuild distaccato con log → recreate alla convergenza → gate funzionali a mano (health/smoke/telemetry-report/e2e router).
- `pgrep -fa <pattern>` eseguito dentro un commando shell che CONTIENE quel pattern fa **self-match** (la riga `/bin/sh -i -c ... pgrep -fa 'x|y'` matcha se stessa) → falsi positivi («build_vivo» dopo la fine reale) e falsi negativi (pattern composto con `|` in pgrep senza `-f` esteso può matchare a vuoto). Misurare lo stato da artefatti (image tag `CreatedSince`, file, DB), non da pgrep. Evidenza: laya d9 (2026-11-09, 3 occorrenze nella stessa sessione) e hal_system2 (sessione pregressa, same class).

## Output lunghi restituiti a frammenti

- `terminal` e `read_file` possono restituire risposte lunghe come **frammenti tagliati o disordinati** (righe di sezioni diverse, output mancante) mentre i file su disco sono integri: non concludere che uno script sia corrotto dal display. ## `grep`/`find_path`: pattern matchati sul path completo dalla root

- `include_pattern` viene matchato sul **path completo a partire dalla root di progetto** (es. `brainbeez/services/api/src/**`): un pattern `services/api/src/**` o `web/src/**` restituisce «No matches» su contenuti reali → falso negativo a rischio di design se una decisione si basa su «assenza» non confermata. Usare il prefisso root, oppure `**/web/src/**/*.js` (glob radiale) + filtro successivo; attenzione alla semantica incoerente: path di file singolo senza prefisso (`docs/product/prd.md`) funziona, i glob di sottorecarte no.
- **Stessa semantica per `find_path`**: i glob sono matchati sul path completo dalla
  root — `web/**/*` non trova nulla anche se `web/src/*.js` esiste, `**/*.py` sì; la
  regola «pattern senza radice = falso negativo» vale per entrambi i tool.
- Regola pratica: prima di concludere «il simbolo non esiste», ri-verificare l'assenza con una seconda query (pattern radiale o senza `include_pattern`).

## `docker compose run` ucciso da fuori: container orfani e hang

- Se il client (tool cancellato, sessione chiusa, terminale killato) muore durante `docker compose run --rm …`, la cleanup `--rm` **non scatta**: il container resta orfano «Up» e continua a eseguire la suite (osservato: `pytest -q` orfano a metà run, restando vivo per ore). Verificare sempre `docker ps --format '{{.Names}}\t{{.Status}}'` prima di concludere che il gate «non ha fatto in tempo»; pulizia con `docker rm -f <run-*>`.
- Per gate lunghi da terminal: involucro `timeout N sh -c 'cmd > log 2>&1; ec=$?; …'` (exit 124 = bounded, exit reale catturato dal log) — mai dichiarare green da run interrotto (policy L1 «verità del gate»); per hang sospetti di Python dentro compose: `timeout -s ABRT` + `PYTHONFAULTHANDLER=1` per ottenere lo stack prima del kill.
- Gate lunghi lanciati dal contesto dell'agente: `test_run` muore al **context server request timeout** (kill esterno: container orfano in corsa, log mai scritto) e `nohup cmd &` muore silenziosamente alla chiusura della pty (log tronco, nessun riassunto); con `--rm` il container auto-rimosso non lascia alcun exit code consultabile. Unico pattern con prova del verdetto: `setsid sh -c 'cmd > log 2>&1; echo EXIT_CODE=$? >> log' < /dev/null &` + polling del marcatore con loop bounded (parametri numerici del tool inaffidabili, §sopra); mai dichiarare green senza marcatore.
- Diagnosi hang prima di accusare la contesa compose: un gate bounded restituisce **EXIT=124** = il comando è *appeso*, non fallito. Ordine: (a) leggere l'exit reale; (b) `docker ps` per orfani `*-run-*` di run interrotte (rm solo su quelli); (c) verificare che il **runner chiuda gli handle**: un mount jsdom con `setInterval`/WebSocket pendente tiene vivo `node --test` all'infinito e produce lo stesso sintomo di una corsa compose bloccata. Regola L2 sorella: «ogni vista montata nei test ha il suo dispose nel teardown».
- Evidenza: brainbeez /cycle CIC (2026-11-08: due hang «docker» diagnosticati a ritroso — orfano `web-run-*` Up 19 min da run cancellata + mount di `views/board.js` senza `afterEach(disposeBoard())`; il mutex compose del progetto (lock canonico) esisteva già ma non copriva i run diretti fuori canone).

## Shell di lavoro `sh`/dash: sostituzione di processo e quoting `bash -c` annidato

- Il tool terminal esegue in **`sh`/dash**, non bash: `<(...)` (process substitution) fallisce con `Syntax error "(" unexpected` e il quoting `bash -c` annidato può fallire (exit 2). Per confronti fra output/file: `python3` in heredoc o **file temporanei reali** (`cmd > /tmp/a.txt; cmd2 > /tmp/b.txt; diff /tmp/a.txt /tmp/b.txt`). Stessa famiglia: il writer canonico per JSON (sezione «Writer canonico per handoff JSON»).
- Regola pratica: prima di ogni `<(`/pipe dinamica in un comando, riscrivere con file temporanei o python heredoc — il fallimento è *parziale* (la shell può eseguire metà comando) quindi mai fidarsi di exit 0 in catene miste.
- Evidenza: brainbeez /todo rv17 (2026-11-07: process substitution `<(...)` sotto sh fallita durante la verifica d'àncora, nota «onestà» della voce) e brainbeez /cycle CIC (2026-11-08: `diff <(cat f) <(docker run ...)` scartata con `/bin/sh: 2: Syntax error "(" unexpected` in sessione diversa — **seconda evidenza**, promozione ammissibile ex policy ≥2 sessioni; riparato con file in /tmp; nella stessa run `timeout_ms` respinto di nuovo → §Parametri numerici).
