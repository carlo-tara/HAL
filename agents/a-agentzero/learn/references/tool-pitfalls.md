## Parametri numerici respinti come stringhe

- `read_file` con `start_line`/`end_line` e `terminal` con `timeout_ms` possono fallire con `invalid type: string, expected u32/u64` anche con valori numerici → non insistere: per i range usare `sed -n '<A>,<B>p' <file>` via terminal; per `terminal` omettere `timeout_ms` (il default basta per comandi brevi).
- Evidenza: sessione `/graph -y` Gate 5/6 (2026-10-26, 3 occorrenze), sessione graph-cycle-sync-todo (2026-10-21, `product/session-learnings.md` § "Tool pitfalls Zed editor"), sessione /learn Kimi dynamic-tool-loading (2026-10-28: `read_file` con range righe respinto 3×, `timeout_ms` respinto 1×; entrambi aggirati con `sed -n`/omissione), sessione QwenCloud multi-turn (2026-10-28: `read_file` con range respinto 2×, stesso identico errore anche a parametri numerici → `sed -n`) e sessione QwenCloud connection-pooling (2026-10-28: `read_file` con range respinto 4× in due tentativi paralleli, identico errore `invalid type: string, expected u32` → `sed -n` via terminal) e sessione QwenCloud async-task-management (2026-10-28: `read_file` con range respinto 3× anche con un solo parametro, `terminal timeout_ms` respinto 2× → `sed -n`/omissione) e sessione QwenCloud streaming (2026-10-28: `read_file` con range respinto 2× anche con parametri numerici → `sed -n`) e sessione QwenCloud models-catalog (2026-10-28: `terminal timeout_ms` respinto 2× con errore identico `invalid type: string, expected u64` → omesso) e sessione diagnosi Laya ABSTAIN (2026-10-29: `read_file` range respinto 3× anche con parametri numerici, `terminal timeout_ms` respinto 1× → `sed -n`/omissione) e sessione fix laya_service + /learn (2026-10-29: `read_file` con `start_line`+`end_line` respinto 2× in due chiamate, `terminal timeout_ms=60000` respinto 1× → `sed -n`/omissione).

## Batch `edit_file` non atomico

- Se un edit del batch non combacia, la chiamata si interrompe: gli edit **prima** sono applicati, quelli **dopo** no → dopo un failure, rileggere il file e riapplicare solo i mancanti con il testo esatto corrente.
- Un formatter/reflow tra un turno e l'altro può spezzare liste YAML/Markdown (es. `tests: [a, b]` su più righe) e far fallire `old_text` multiriga → preferire ancore a riga singola o rileggere sempre prima di un nuovo batch.
- File condivisi mutati da sessioni parallele tra lettura e scrittura invalidano le ancore come il reflow (es. `./ToDo.md` o questi reference, con delta/evidenze accodati da altre sessioni): rileggere prima di ogni batch. Non usare due edit a cascata con ancore sovrapposte nello stesso batch: se l'edit prima rimuove parte del testo che l'edit dopo usa come ancora, si tronca contenuto (stato intermedio applicato) → una inserzione = un edit.
- Evidenza: `product/state/work-graph.md` (2026-10-26, batch interrotto all'indice 1 con YAML riflow; listini `tests:` multiriga) e sessione QwenCloud async-task-management (2026-10-28: `ToDo.md` e `tool-pitfalls.md` mutati da sessioni parallele tra le letture, ancore invalidate; un batch con 2 edit a cascata ha troncato il titolo della voce P0, ripristinato alla chiamata successiva) e sessione QwenCloud streaming (2026-10-28: `ToDo.md` cresciuto 67→151 righe tra lettura e scrittura per append concorrenti, index 1 di un batch di 2 edit fallito → rilettura della coda reale e riapplicato solo il mancante) e sessione fix naming L2 harness-* (2026-10-31: `.agents/skills/harness-wtp/SKILL.md` passato da 1.1.4 a 1.1.5 tra due letture nello stesso turno, mtime 12:00 in mezzo; non era un reflow: vera scrittura concorrente).

- **Mai ricostruire `old_text` a memoria**: rileggere sempre l'area bersaglio prima di ogni `edit_file` (dopo formatter esterni o altre sessioni le ancore cambiano sito e il fuzzy applica il testo dove non deve). Evidenza: brainbeez 2026-10-28 §«Formatter in guerra» (editor 88 col contro gate `ruff format` 100) e 2026-10-30 (ri-edit di file re-formattati dal gate prima della stesura).
- **Un solo `edit_file` per file per chiamata**: un secondo edit sullo stesso file nello stesso batch è vietato anche con ancore non sovrapposte — il primo edit sposta gli offset e il fuzzy del secondo può colpire un'ancora _simile_ (stesso pattern, variabile diversa `body`/`response.text` → file incoerente, NameError latente). Inserzioni multi-punto = N chiamate + rilettura. Evidenza: brainbeez `session-learnings.md` §HAL 2026-10-28 (scambio di contenuto, non troncamento) e batch a cascata su `ToDo.md` 2026-10-28 (titolo P0 troncato).
- **Tabelle markdown a colonne padded**: àncore di fine-riga inutilizzabili (spazi ignoti in coda); append e correzioni di righe tabellari via `cat >>` heredoc quotato da terminal, non via `edit_file`. Evidenza: brainbeez `ToDo.md`/`agent-progress.md`/`work-graph.md`, ondate 2026-10-28 → 2026-10-30 (canone di append dei re-run, nessun fallimento di àncora).

## Writer canonico per handoff JSON

- `product/state/handoff-<kind>.json` si scrive con `bash agents/scripts/harness-prompt-builder.sh handoff-write <kind> --field summary='…' --field files=… --field next=…` (default `product/state/` **risolto dalla root dello script**, `ts`/`cmd`/`token_budget` auto-compilati), non con `write_file` a mano: la scrittura manuale rischia schema drift e campi stale; dove i comandi citano `scripts/harness-prompt-builder.sh`, dalla root HAL il path va risolto in `agents/scripts/`.
- **Workspace consumer:** il default `product/state/` è relativo a `hal_gateway/`, non al repo attivo → senza `--out` l'handoff finisce nella root HAL (shadow copy). Da consumer passare **sempre** `--out product/state/handoff-<kind>.json` (path relativo alla cwd del progetto).
- Evidenza: sessione graph 2026-10-27 (meccanica handoff via tool, nota `--dir` poi allineata al default) e sessione /learn QwenCloud streaming 2026-10-28 (handoff scritto a mano via `write_file`, poi normalizzato con `handoff-write todo`; confermato default `product/state/`); sessione /todo+/graph brainbeez 2026-10-28 (shadow stale in `hal_gateway/product/state/handoff-todo.json` dal 2026-10-26; risolta con `--out` esplicito su tutti i kind, todo e graph).

## Output lunghi restituiti a frammenti

- `terminal` e `read_file` possono restituire risposte lunghe come **frammenti tagliati o disordinati** (righe di sezioni diverse, output mancante) mentre i file su disco sono integri: non concludere che uno script sia corrotto dal display. Verificare con comandi corti e mirati (`grep -n`, `sed -n` ≤25 righe, `wc -l`, `print(repr(...))` su riga singola) prima di ogni riscrittura.
- Corollario per `edit_file`: dopo il reflow del formatter i blocchi lunghi non matchano più → ancorare `old_text` a righe brevi e uniche, e dopo un fallimento rileggere l'area (già in "Batch non atomico").
- Evidenza: sessione takeout→Proton 2026-10-26/27 (>10 occorrenze su `sed`/`read_file`/output rclone).

## `list_directory` con path `.` restituisce vuoto

- `list_directory` con path `.` (o altro path non radice) restituisce stringa vuota senza errore: usare sempre il nome della root di progetto (es. `hal_gateway`) o un path che la includa come primo componente; per il summary senza path usare `diagnostics` o `find_path`.
- Evidenza: sessione Kimi 2026-10-28 (osservazione singola, esclusa con nota «radice non verificata») e sessione QwenCloud multi-turn 2026-10-28 (`.` → vuoto, `hal_gateway` → ok: radice verific per contrasto).

## Frammenti CJK nel testo italiano generato

- Frammenti cinesi (es. `工作`) possono insediarsi nel testo italiano generato, sia negli `old_text`/`new_text` di `edit_file` sia negli heredoc `terminal`: dopo ogni scrittura di contenuti lunghi, verificare con `grep -rnP '[\x{4e00}-\x{9fff}]' <file/target>` prima del commit (exit 1 = pulito); il rimedio è riscrivere il frammento, non affidarsi alla rilettura visiva.
- Evidenza: sessione QwenCloud doc-review 2026-10-28 (3 artefatti in `ToDo.md` + 1 in `cache-layer-priority.md`, intercettati con verifica post-scrittura; candidato aperto in `product/session-learnings.md` con regola «aprire voce alla seconda sessione») e sessione QwenCloud models-catalog 2026-10-28 (frammento in print di diagnostica terminal; file committati risultati puliti dalla stessa verifica → scope esteso oltre `edit_file`).

## Path dei comandi L0: canonico vs mirror generato

- `edit_file`/`write_file` non risolvono gli symlink intermedi del workspace: path sotto `agents/...` restituiscono `path not found`, path assoluti fuori progetto `parent directory doesn't exist`. Per le skill L1/utility usare l'alias `.agents/skills/<nome>/...` (symlink → risolve sullo stesso file canonico); per i file fuori progetto (es. `hal_gateway/tests/`) usare il terminale con heredoc quotato (`cat > <path> <<'EOF'`).
- Attenzione: per i comandi L0 il canonico è `a-agentzero/commands/<cmd>.md` e l'alias `.agents/skills/<cmd>/SKILL.md` è un **mirror generato** da `link_zed_skill` — l'edit "sembra" riuscito ma il `/sync !` successivo lo sovrascrive (caso graph 1.0.3, 2026-10-30: bump committato sul mirror, poi annullato dal deploy). Sul canonico agire via terminal (python/sed), poi rilanciare `bash agents/scripts/link-workspace-skills.sh` e verificare il mirror allineato.
- Evidenza: sessione `/learn !`+`/sync` 2026-10-30 (edit_file su `agents/a-harness/...` respinto → alias `.agents/skills/...`; write_file su `hal_gateway/tests/` respinto → heredoc terminale) e sessione `/version`+`/commit` 2026-10-30 (mirror graph 1.0.3 ripristinato da `/sync !` perché il canonico era indietro; contratto `hal_gateway/tests/test_l0_command_canonical.py`).
